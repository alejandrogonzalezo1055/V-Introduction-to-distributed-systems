\section{Modelos del sistema}
\label{sec:models}


A continuación se explican los modelos que usa el sistema de reservas.


\subsection{Modelo Arquitectónico}
\label{sec:models_arch}

El sistema tendrá un modelo de 3 capas, como se observa en (\cref{fig:model_capas}).

\begin{figure}[htbp]
	\includegraphics[width=0.7\textwidth]{Images/Modelo de capas sistema.png}
	\caption{Modelo arquitectónico de n capas del sistema}
	\label{fig:model_capas}
\end{figure}

La \textbf{capa de consumidores} se encarga de pasarle solicitudes y peticiones de los clientes al gestor de transacciones. Cada cliente puede hacer peticiones de reservas, modificación, consulta, y cancelación de reserva.

La \textbf{capa de servicios} tiene dos procesos distintos. El \textit{gestor de transacciones} enruta las peticiones del sistema a su canal sincrono que se encarga de las solicitudes de reserva, modificación, y consultas mediante el proceso Reservas/Modificaciones/Consultas y se comunicara con las demas capas mediantes el patrón REQ/REP; o al canal asincrono, que usando el servicio de cancelación de reservas y mediante el patrón PUB/SUB se encarga de las solicitudes de cancelación pues estas no requieren notificar al cliente.

Finalmente la \textbf{capa de almacenamiento} se encargara de garantizar la persistencia de las reservas de todo el sistema, esto lo hara mediante operaciones CRUD hacia una base de datos Postgrace SQL. 


\subsection{Modelo de Interacción}
\label{sec:models_exch}

El sistema, como se menciona en \cref{sec:models_arch}, manejara peticiones de forma sincrona y asincrona. El proceso RMC se controlara por medio de un proceso sincrono, pues la buena detección de errores ayuda a conservar la integridad de los datos. El sistema de cancelación no necesita saber si cada cliente recibió o no la notificación de su solicitud realizada, lo que contribuye a la mejora del rendimiento del sistema.
