    Módulo 0 · Infraestructura

    PostgreSQL en un contenedor

    Un contenedor trae PostgreSQL ya instalado y aislado del sistema. Lo levantan y lo borran con un comando, y todos en el equipo tienen exactamente la misma versión.

    1. Instalar Docker (Ubuntu 22.04 o superior)

    En la VM de la universidad

    Instalar Docker requiere sudo. Prueben pronto si la VM de almacenamiento lo permite. Si no, el plan B es instalar PostgreSQL directo con apt; el código de SQLAlchemy no cambia.

    2. Describir el contenedor: compose.yaml

    Pónganlo en la raíz del proyecto, junto al .env.

    • 127.0.0.1:5432:5432 publica el puerto solo para la misma máquina. Persistencia y PostgreSQL viven en la misma VM, así que no hace falta abrirlo a la red.
    • El volumen pgdata guarda los datos fuera del contenedor. Si borran el contenedor, los datos siguen ahí.
    • El healthcheck le dice a Docker cuándo PostgreSQL ya acepta conexiones. Arrancar tarda unos segundos.

    3. Comandos del día a día

    4. Mirar la base por dentro

    La trampa más común

    Las variables POSTGRES_USER, POSTGRES_PASSWORD y POSTGRES_DB solo se aplican la primera vez, cuando el volumen está vacío. Si después cambian la contraseña en el archivo, el contenedor sigue con la vieja y verán password authentication failed. Solución: docker compose down -v (borra los datos) y volver a levantar.

    Módulo 2 · Conceptos

    Cómo se organiza SQLAlchemy

    Cuatro piezas aparecen en todo el código.

    PiezaQué esCuántas crear
    EnginePunto de acceso a la base, con su pool de conexiones.Una por proceso, al arrancar.
    ConnectionUna conexión prestada del pool. Se usa en Core.Una por operación, dentro de un with.
    SessionUna conexión más el seguimiento de objetos. Se usa en el ORM.Una por petición, dentro de un with.
    MetaDataEl catálogo de tablas. Sirve para crearlas y borrarlas.Una para todo el esquema.

    ¿Core u ORM?

    • Core es SQL con sintaxis de Python. Ves exactamente qué se ejecuta y trabajas con filas.
    • ORM mapea clases a tablas. Trabajas con objetos y la Session decide cuándo escribir.
    • Se pueden mezclar: dentro de una Session se ejecutan sentencias de Core. Es lo que conviene para reservar.

    Escojan un estilo para Persistencia y úsenlo en todo el servicio. Esta guía enseña ambos para que decidan con criterio.

    Módulo 3 · Core

    Definir las tablas del SRB

    Un evento tiene una o dos ocurrencias, y cada ocurrencia lleva su propio cupo. Los nombres de columna siguen su diagrama de clases.

    Para ocurrencia, create_all envía algo parecido a esto (con echo=True lo ven exacto):

    • Las columnas se acceden con .c: ocurrencia.c.fecha.
    • UniqueConstraint("evento_id", "fecha"): el RMC identifica una ocurrencia por evento y fecha, así que esa pareja no se puede repetir.
    • create_all crea las tablas que faltan y no modifica las existentes. Si cambian una columna, vuelvan a correr la carga con drop_all.
    Por qué el CHECK

    La restricción ck_cupo hace que PostgreSQL rechace cualquier escritura que deje más puestos ocupados que la capacidad. Aunque el código tenga un error, la base no permite sobreventa.

    Módulo 5 · Core

    Actualizar, borrar y transacciones

    En SQLAlchemy 2.x nada se guarda sin commit. Hay dos formas de manejarlo:

    La operación más importante del SRB es reservar sin sobrevender. PostgreSQL hace la suma y la verificación en una sola sentencia, y rowcount dice si hubo cupo.

    • .returning(reserva.c.id) devuelve el id generado. Funciona en PostgreSQL.
    • El return dentro de engine.begin() sale del bloque normalmente, así que hace commit. Una excepción haría rollback.
    Decisión de diseño

    Para cancelar (segunda entrega) pueden borrar la fila o poner estado = False. Marcar conserva el historial, y eso ayuda a mostrar el estado de la BD en la sustentación.

    La Session y el CRUD

    La Session lleva la cuenta de los objetos que crean o cargan, y al hacer commit escribe los cambios. Toquen cada estado para ver qué significa.

    → add() → flush → close()

    Crear

    Leer

    • session.scalars(...) devuelve objetos. session.execute(...) devuelve filas con varias columnas.
    • .all() da una lista, .first() el primero o None, y .one() exige exactamente uno.

    Modificar y borrar

    Trampa con concurrencia

    Leer un valor, sumarle en Python y guardarlo funciona con un solo cliente y falla con varios. Para contadores como puestos_ocupados, dejen que la base haga la suma.

    Módulo 8 · ORM

    Relaciones y cuándo se cargan

    Por defecto, evento.ocurrencias no se carga hasta que se toca. Dentro de un ciclo eso dispara una consulta por cada evento: el problema N+1.

    Con 50 eventos cargados, una consulta del mes hecha con la carga por defecto hace decenas de viajes a la base. Eso se nota en los tiempos de respuesta de la Tabla 1.

    El contrato, operación por operación

    tipo que llegadatos que lleganrespuesta
    CONSULTA{"mes": "noviembre"}EXITO + lista de eventos (formato por acordar)
    CONSULTA_DISPONIBILIDAD{"id_evento": "E1", "fecha": "2026/11/07"}EXITO + {"capacidad_total", "ocupacion"}, o FALLO + NO_EXISTE
    AGREGAR_RESERVA{"id_evento", "fecha", "n_asientos"}EXITO + {"id_reserva"}, o FALLO + SIN_CUPO
    Tres detalles que fallan en silencio
    • Las claves de la respuesta de disponibilidad son capacidad_total y ocupacion, aunque las columnas se llamen capacidad y puestos_ocupados.
    • La fecha llega con barras (2026/11/07). date.fromisoformat falla con ese formato.
    • El mes llega como texto en español. Su número es la posición en la lista meses de mensajes.py más 1.

    Traducir los datos del contrato

    Dos operaciones resueltas

    • Un engine y un sessionmaker por proceso, creados al arrancar el servicio.
    • Una transacción por petición. Nada de Sessions que vivan todo el tiempo.
    • Las funciones devuelven datos; el main arma la Respuesta con crear_rta y el mismo uuid de la petición.
    • La CONSULTA queda como ejercicio (módulo 13).
